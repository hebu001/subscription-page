## F05: секреты в журналах ошибок

Исправлены следующие пути:

- `backend/src/common/axios/axios.service.ts`: все семь операций панели, включая
  metadata при старте, конфиги, пользователя и подписку. В журнал передаются
  постоянное сообщение, имя операции и allowlist `errorType`, `code`, HTTP `status`.
  Тела ответов/запросов, Axios config, URL, заголовки и исходные сообщения ошибок
  больше не передаются в logger. Ожидаемый 404 подписки по-прежнему возвращает `null`.
- `backend/src/common/utils/filter-logs/{safe-error,filter-logs,logger-format}.ts`:
  общий формат используется приложением и тестами. Он отбрасывает произвольные
  вложенные метаданные и `stack`, переводит распознанные структуры ошибок в
  безопасную диагностику до финального Nest/Winston форматирования. Проверены
  формы `Logger.error(error)` и `Logger.error(message, error)` для Error/AxiosError.
  Дополнительно маскирует
  известные секреты окружения, URL и обозначенные значения credentials в строках.
- `backend/src/modules/root/root.service.ts`: ошибки выдачи страницы/подписки
  используют безопасную диагностику. Debug-журнал Marzban больше не содержит
  ключи, токены, подписи, декодированный payload или username.
- `backend/src/modules/root/root.controller.ts` и `subpage-config.service.ts`:
  удалено журналирование пользовательского clientType, идентификаторов конфигурации
  и полного результата ошибки валидации конфигурации.
- `backend/src/common/exception/httpException.filter.ts`: журнал не содержит URL
  запроса и произвольные сообщения/ответы исключений. HTTP-ответ клиенту сохранён.
- `backend/src/common/middlewares/check-assets-cookie.middleware.ts`: ошибка
  проверки cookie содержит только безопасную диагностику.
- `backend/src/common/middlewares/proxy-check.middleware.ts`: debug пишет результат
  проверки наличия proxy/HTTPS, а не значения недоверенных X-Forwarded-* заголовков.
- `backend/src/main.ts`: конфигурационный префикс не выводится в журнал.

Исходные stack/message ошибки намеренно не служат источником диагностики: они могут
содержать приватные URL и произвольные upstream данные. Сохранены контекст Nest,
операция, тип ошибки, известный системный/Axios code и HTTP status. Маскирование
строк — дополнительная защита, а не универсальный детектор секретов: новые сообщения
не должны интерполировать запросы, пользовательские данные или исходные ошибки.

У `nest-winston` вызовы `warn(error)`, `debug(error)` и `log(error)` могут потерять
признак Error ещё до общего formatter. Обычный Error без распознаваемых полей
`config`/`request` в этих формах не покрывается общей гарантией маскирования.
Все новые места журналирования ошибок на любом уровне должны применять
`safeErrorDiagnostics(error)` **до** вызова logger и добавлять постоянное сообщение.
В исправленных действующих обработчиках это правило соблюдено; центральный formatter
служит дополнительной защитой, а не заменой обработки ошибки в месте вызова.

## F06: приватные ссылки в access log

`backend/src/common/middlewares/access-log.middleware.ts` заменяет прежний Morgan
формат в `main.ts`. Каждый запрос получает новый серверный `X-Request-ID`;
входящий ID не принимается как доверенное значение.

Запись — JSON с временем, методом, известным шаблоном маршрута, status, outcome,
responseTimeMs, durationMs и requestId. Для кастомного префикса сохраняется маркер
`/:customPrefix`. Для неизвестных маршрутов, статики и ранних отказов используется
`[unmatched]`, без подстановки исходного пути. Прерванный до отправки заголовков
запрос имеет status `null` и outcome `aborted`, а не ложный 200. Если Morgan
не успел получить timing для такого разрыва, responseTimeMs/durationMs также
сохраняются как `null`; измерение не подменяется фиктивным числом.

Middleware подключён до proxy/cookie/static/body-parser проверок, поэтому безопасный
формат охватывает ранние отказы и разрывы сокетов. В access log не попадают URL,
query string, короткий UUID, invoice token, Referer, User-Agent, Cookie, Authorization,
входящий request ID или X-Forwarded-* значения. Старое переопределение Morgan token
`remote-addr` удалено; вычисление clientIp для upstream-запросов сохранено.

## Проверка

Из каталога `backend`:

```sh
npm run test:logging
npm run test:payments
npm run test:security
npm run build
npm run lint
```

- `test:logging`: 8 тестов, 8 прошли, без пропусков. Захватывают окончательные
  строки через реальный Nest Logger → Winston → production `nestLike` formatter;
  воспроизводят ошибки всех семи операций панели, вызовы `Logger.error(error)` и
  `Logger.error(message, error)`, вложенные метаданные и интерполированные строки
  с dummy-секретами. Отдельная регрессия проверяет enumerable code/context/operation
  и другие поля Error **с полем config**, распространяемые Nest в итоговые метаданные
  при `error`/`warn`/`debug`/`log`; это не тест обычного Error без config для всех уровней.
- HTTP → Morgan: реальный локальный сервер, default/custom prefix, маршруты страницы
  и оплаты, config endpoint, статический файл, 404, ранний 403 и разрыв сокета.
- Дополнительно проверены зарегистрированные маршруты настоящих Nest-контроллеров
  с неизменённым payment guard (401 без сессии) и исключением config endpoint из
  global prefix. Внешние сервисы заменены локальными заглушками; вызовов панели нет.
- Независимая проверка дополнительно охватила 24 локальных HTTP-сценария и семь
  сценариев действующего legacy/JWT decoder RootService без утечки ключей,
  username и подписанных токенов. Отчёт и воспроизведения находятся за пределами
  репозитория: `audit/frontend-backend-2026-09-06/fix-verification/INDEPENDENT_F05_F06.md`.
- `test:payments`: 6/6; `test:security` (Origin/Fetch-Site): 4/4.
- Сборка Nest и полный ESLint backend прошли.

Для локальных HTTP-тестов требуется разрешение на bind к `127.0.0.1`: первый запуск
в sandbox остановился с EPERM, затем тесты прошли с разрешённым loopback-доступом.
В тестах используются только dummy-секреты, временные файлы и локальные HTTP-запросы.

- Рабочие логи сервера, старые журналы и внешний reverse proxy не проверялись.

- Формат access log меняется на JSON. Потребители прежнего текстового формата должны
  быть согласованы при выпуске.
- Правила авторизации, ownership, Origin, финансовая логика и ответы API не ослаблялись.
- F01–F04 и F07 остаются отдельными последующими этапами.
